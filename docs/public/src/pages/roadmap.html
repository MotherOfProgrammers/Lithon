The three phases

One core.
Three horizons.

The phases are a dependency chain, not three parallel tracks. Phase II cannot start until the emitter produces the same bytes everywhere, and Phase III cannot start until the emitter can be pointed at hardware rather than only at the machine's userland.

Shipped

CPUID parsed and cross-checked against the kernel, so the AVX and AVX-512 gates cannot silently mis-detect and emit an instruction the host does not have. This is the prerequisite Phase III leans on, and the reason its vector work is a matter of writing the emission rather than of proving the machine can take it.

Shipped

A scanner that disassembles each function and flags legacy SSE after a VEX prefix with no vzeroupper. No AVX is emitted yet, so this is a guardrail laid before the road. Its --self-test mode proves the scanner actually fires, which is the difference between a guardrail and a decoration.

tools/check_vex_transitions.py --self-test proves the scanner fires

Shipped

A block whose types cannot be established runs on the C++ interpreter instead of guessing, and --strict converts that fallback into a refusal. That flag is what makes the tier line in the output worth reading: a clean exit under --strict is proof the bytes were emitted and ran, where --auto can hide a total fallback behind output that happens to look right.

tier_runner --auto · src/jit/print_guard.h

Control-flow graph and dominators, iterated dominance frontier Phi placement, Mem2Reg, copy propagation, CFG liveness, interference-graph allocation, and register coalescing so a merge can adopt a dead source’s register. The honest size of that last win is five merges across the typed regression corpus, and the Phase I page explains why it is not more.

In progress

25 of 26 IR opcodes are emitted; this is the last one. Today a merge is lowered into a store on each predecessor edge plus a load at the join. The liveness prerequisite has already landed in compute_edge_uses(). What is owed is value-kind inference for a float merge, an allocator slot for the result, and codegen for the join’s parallel copies — and that last one is the same interference problem as phase 2.8, so it relocates the coalescing question rather than shrinking it.

Next

Write the object headers directly — program headers, section table, entry point — instead of linking against an external toolchain. It is the same kind of work as the encoder, and for the same reason: a header is a byte format, so it can be got exactly right and then checked exactly.

depends on a byte-stable emitter across both host ABIs

Next

A .py file compiled into a native binary small enough to email, with no interpreter and no runtime beside it. The budget decides the design rather than being checked at the end: a statically linked libc will not fit in it, so there is no printf and no malloc, and anything the program prints has to be formatted by emitted code.

size budget is the real constraint, not the feature list

Next

The emitted binary must not need the Lithon interpreter to run, which means every place emitted code currently calls back into the engine has to become either emitted code or a trap instruction in the image. Division by zero already qualifies; the shared double formatter is the expensive case.

touches the shared float formatter first

Planned

The 0F 05 instruction written straight from source syntax, so a Lithon program can talk to the kernel without a libc in between. It is also the largest behavioural step in the roadmap: the emitter currently assumes a hosted C entry point, and a freestanding image has neither a stack frame nor a return address by default.

needs the emitter to stop assuming a hosted C entry point

Planned

Expose a raw pointer to a native array and let Lithon mutate it in place, with no copy on the way in or out. The type checker still gets a vote: a pointer is a type like any other, and an operation that would write through it to something narrower is refused at compile time.

depends on Phase II decoupling landing first

Planned

Parallel list processing across a vector unit. The detection gate and the VEX transition guardrail are already in place underneath it; no AVX is emitted yet.

cpu_features.h gates it · check_vex_transitions.py keeps it honest

Planned

The genuinely architecture-neutral layers already exist: ir/, liveness.h and optimize.h name no registers at all. What is missing is a second encoder, which makes this a reach question rather than a design one.

What counts as shipped here

A feature is marked shipped when a test exists that fails if the feature regresses, not when the code is present. That is why every milestone carries evidence, and why two entries are marked in progress despite working: the Win64 ABI has no test evidence yet, and Phi is emitted by lowering rather than by a code path of its own.

It is also why there is no percentage on this page. A number that cannot be derived from a test is a decoration, and this tracker would rather show you the tests.
